# Архитектура сквозного шифрования SALOM

Первый прототип охватывает личные сообщения между Android и Windows с двумя устройствами на аккаунт. Рабочие чаты остаются в текущем режиме. Для групп нужен отдельный проект протокола назначения ключей, смены состава и восстановления.

## Выбор реализации

Для прототипа рассмотрим Signal Protocol с PQXDH и Double Ratchet. Спецификация Sesame описывает принципы управления несколькими устройствами. Библиотека libsignal предоставляет официальные интерфейсы Java, Swift и TypeScript для приложений Signal. Внешнее применение не поддерживается, готового поддерживаемого интерфейса .NET нет. До интеграции в WPF необходимо подтвердить лицензирование, сопровождаемость адаптера, раздачу подписанных бинарников и доступность обновлений безопасности. Проверка включает сопоставление тестовых векторов и обмен Android ↔ Windows. Схему шифрования SALOM самостоятельно не разрабатывает.

- [libsignal](https://github.com/signalapp/libsignal)
- [PQXDH](https://signal.org/docs/specifications/pqxdh/)
- [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)
- [Sesame](https://signal.org/docs/specifications/sesame/)

## Устройства и ключи

- Каждая установка создаёт собственную идентичность. Сервер получает публичный ключ, подписанные и одноразовые предварительные ключи. Выдача одноразового ключа атомарна. Серверный SALOM JWT разрешает регистрацию устройства, но сам по себе не подтверждает новый ключ собеседнику.
- Новое устройство подтверждается уже доверенным устройством через одноразовый сеанс сопряжения с проверкой ключей. Отпечатки собеседников проверяются QR-кодом или кодом безопасности. При изменении проверенного ключа отправка останавливается до явной проверки пользователем.
- На Android Android Keystore оборачивает локальный ключ, которым шифруется хранилище протокола. На Windows применяется DPAPI текущего пользователя для защиты локального ключа. Закрытые ключи, состояние Ratchet и открытый текст исключаются из серверного backup и логов.

## Сообщения и вложения

- Для каждого устройства адресата и остальных устройств отправителя создаётся отдельный конверт. Сервер проверяет аккаунт, адресацию и право синхронизации, хранит конверты, выставляет ограничения и поддерживает прежний постоянный `client_message_id` для повторной отправки. Запись нового состояния сеанса и шифротекста в исходящую очередь атомарна. Повторная отправка использует уже записанный конверт.
- Вложения шифруются на клиенте с индивидуальным ключом и аутентифицированным форматом выбранной реализации. Ключ, ожидаемый хеш, имя и MIME передаются внутри шифрованного сообщения. Клиент проверяет целостность до открытия вложения. На экране блокировки показываются только общие push-уведомления.
- Переключение выполняется для явно обозначенного E2EE-диалога после проверки возможностей всех устройств. При неподдерживаемом устройстве отправка шифрованного сообщения блокируется. Исторические сообщения не получают задним числом статус E2EE.

## Потерянное устройство и восстановление

Пользователь отзывает потерянное устройство с доверенного клиента. Сервер прекращает выдачу конвертов ему и доставляет обновлённый список устройств. Собеседники устанавливают новые сеансы при изменении идентичности. Без оставшегося доверенного устройства вход восстанавливает аккаунт и создаёт новую идентичность. Восстановление зашифрованной истории проектируется отдельно через проверенный резервный формат с секретом восстановления, который хранит пользователь.

## Условия выпуска

Тестовые векторы и совместимость Android ↔ Windows, перестановка и повтор доставки, одноразовые ключи, смена устройств, отзыв и восстановление, повреждённые вложения, потеря сети во время атомарной записи и проверка защиты от понижения режима. Перед включением на пользовательских аккаунтах требуется независимая проверка реализации и миграции. Сквозное шифрование не входит в сборку 0.15.7.
